# 15. Future Emergency Broadcast (Beta 1 제외)

## 1. 목적
일반 LIVE와 별도로 공공·안전 목적의 **긴급 상황 전파 기능(Emergency Broadcast)**을 향후 기능 후보로 둔다.

사용자가 직접 112/119 신고를 하기 어려운 상태이거나, 말을 할 수 없거나, 위험 때문에 통화가 곤란한 상황에서 주변의 여러 사용자에게 현재 상황을 빠르게 전파하여 **다른 사용자가 신고·도움 요청·현장 대응을 보조할 수 있게 하는 것**이 목적이다.

예시 상황:
- 화재
- 응급 의료상황
- 사고
- 도둑/강도/위협 상황
- 사용자가 말하거나 전화하기 어려운 긴급상황

> 이 기능은 공식 긴급신고 체계를 대체하지 않는다. 사용자가 직접 신고할 수 있으면 112/119 등 공식 신고수단을 우선하도록 한다.

## 2. 기본 개념
```text
Emergency 버튼
    ↓
긴급 유형 선택 또는 즉시 전파
    ↓
현재 위치 + 제한된 실시간 카메라/상황정보
    ↓
주변 사용자에게 고우선순위 경고
    ↓
수신 사용자
  - 상황 확인
  - 공식 신고 진행
  - 신고 완료 표시
  - 필요한 경우 안전한 범위에서 도움 제공
```

## 3. 일반 LIVE와의 차이
일반 LIVE:
- 정보 공유 목적
- 무료 현장정보
- 일반 우선순위

Emergency Broadcast:
- 즉각적인 안전 대응 목적
- 높은 알림 우선순위
- 제한된 반경의 주변 사용자 중심
- 짧은 TTL
- 신고/도움 연결 UX 포함
- 별도 Trust/Safety 정책 필요

## 4. 전파 범위
초기 설계 방향:
- 사용자의 현재 GPS를 중심으로 근거리 사용자에게 우선 전파
- 상황 종류와 밀집도에 따라 반경을 단계적으로 확대 가능
- 정확한 개인 위치를 불필요하게 공개하지 않고, 대응에 필요한 범위만 제공

예시:
```text
1차: 300m
2차: 1km
3차: 필요 시 확대
```

정확한 반경은 향후 실증과 법적·운영 검토 후 결정한다.

## 5. 카메라 LIVE
사용자가 활성화한 경우 현재 카메라 영상을 짧은 Emergency Live Stream으로 공유할 수 있다.

고려사항:
- 사용자가 명시적으로 기능을 실행해야 함
- 기본은 짧은 세션
- 수신자는 주변의 제한된 사용자
- 영상은 일반 LIVE/재판매 정보로 사용하지 않음
- 원본 장기보관을 기본값으로 두지 않음
- 수사/분쟁 등 별도 법적 근거가 필요한 보관은 추후 정책 검토
- 화면 녹화/외부 유출 위험을 고려한 워터마크 및 세션 ID 적용 검토

## 6. 신고 지원
수신 사용자는 예를 들어 다음 행동을 할 수 있다.

```text
[112 신고]
[119 신고]
[신고 완료]
[현장 상황 확인]
[잘못된 긴급전파 신고]
```

중요한 목표는 다수 사용자가 동시에 신고하는 혼선을 줄이는 것이다.

예:
```text
주변 사용자 18명 수신
      ↓
사용자 A: 119 신고 시작
      ↓
시스템: "신고 진행 중 사용자 1명"
      ↓
사용자 A: 신고 완료
      ↓
다른 사용자에게 "신고 완료됨" 표시
```

단, 실제 신고 완료 여부를 플랫폼이 공식기관과 연동해 검증하는 기능은 별도 검토 대상이다.

## 7. 비상 사용자의 입력 최소화
실제 긴급상황에서는 긴 입력을 요구하면 안 된다.

후보 UX:
```text
[긴급 전파]
   ↓
화재 | 의료 | 범죄/위협 | 사고 | 기타
   ↓
[즉시 시작]
```

추후에는 사용자가 말을 하지 못하는 상황을 고려해:
- 무음 실행 모드
- 텍스트 선택형 상태 전달
- 사전 정의 문구
- 카메라만 즉시 시작
등을 검토한다.

## 8. 안전상 중요 원칙
Emergency Broadcast는 악용 가능성이 높으므로 일반 LIVE보다 강한 보호장치가 필요하다.

- 특정인을 공개 추적하거나 보복 목적으로 사용 금지
- 범죄 용의자라고 사용자가 임의 단정하는 표현 제한
- 주변 사용자에게 위험한 현장 접근을 유도하지 않음
- "직접 개입"보다 "공식 신고 및 안전 확보"를 우선
- 정확한 사용자 신원/주소/생활패턴을 불필요하게 공개하지 않음
- 허위 긴급전파 반복 계정에 강한 제재
- 자동 대규모 확산 전에 반경·빈도 제한 필요

## 9. Privacy / Abuse
특히 범죄·위협 상황에서는 카메라 LIVE가 오히려 발신자를 위험하게 만들 수도 있다.

따라서 향후 검토 사항:
- 화면/소리 없는 무음 활성화 UX
- 카메라 활성 여부 사용자가 선택
- Flash/셔터음 등 단말 동작 고려
- 정확한 실시간 위치의 공개 수준
- 가해자가 동일 플랫폼 사용자일 경우 접근 제한 가능성
- 방송 수신 대상의 익명성 및 권한
- 긴급 영상의 저장 기간
- 신고 증거 이용 가능성 및 약관

## 10. Trust / False Alarm
긴급 알림이 잦은 허위 경보로 변질되면 기능 자체의 가치가 사라진다.

향후 고려:
- 사용자 Trust 반영
- 계정/기기별 빈도 제한
- 반복 허위전파 제재
- 주변 다수 사용자 확인 신호
- 신고 완료/오경보 결과 데이터 축적
- 심각한 악용은 계정 정지

단, 신규 사용자라는 이유만으로 실제 위급 상황의 긴급전파를 막는 방식은 피해야 한다.

## 11. 기존 Information Topic과의 관계
Emergency Broadcast는 일반 Information Topic과 완전히 동일하게 처리하지 않는 방향을 우선한다.

```text
Emergency Event
  ├─ initiator
  ├─ emergency_type
  ├─ approximate_location
  ├─ started_at
  ├─ expires_at
  ├─ live_stream(optional)
  ├─ recipients
  ├─ responders
  └─ report_status
```

종료 후 공익성이 있는 비민감 정보만 일반 Place Timeline으로 전환할 수 있다.

예:
- `17:20 화재로 건물 주변 통제` → 공개 Timeline 가능 후보
- 피해자 얼굴/범죄 피해 영상 → 일반 Timeline 전환 금지

## 12. Beta 1 범위
이 기능은 **Beta 1에 포함하지 않는다.**

Beta 1에서는 LIVE/REQUEST/LOCAL First 모델 검증에 집중한다.

Emergency Broadcast는 향후 별도 Prototype 및 법적/운영/안전 검토 후 단계적으로 개발한다.

## 13. 향후 개발 후보 단계
```text
Phase E0
긴급전파 UX / 정책 Prototype

Phase E1
위치 기반 주변 Push + 정적 사진/텍스트

Phase E2
짧은 Emergency Live Stream

Phase E3
신고 진행/완료 협업 UX

Phase E4
공공기관 또는 공식 신고체계 연동 가능성 검토
```

## 14. 핵심 원칙
> 긴급상황의 영상을 널리 퍼뜨리는 것이 목적이 아니라,
> 사용자가 직접 도움을 요청하기 어려울 때 주변의 사람들에게 최소한의 상황을 빠르게 전달하여 공식 신고와 안전 대응이 이루어지도록 돕는 것이 목적이다.
